## 2. Ошибки и пробелы контракта

### P1. Действующий движок нарушает обещание UTF-8, а PCRE2 требует ограничения синтаксиса

§5, §7–8 обещают Unicode matching, валидные `Str` и codepoint ranges.
Текущий `r".".match("я")` даёт `finish == 1` и захват из одного байта `0xD1`:
это половина UTF-8 символа. Это существенный дефект текущей реализации,
который стоит явно поставить перед расширением удобного синтаксиса.

При переходе на PCRE2 одних UTF + UCP тоже недостаточно: `\C` может захватить
отдельный байт. Предлагаю компилировать с `PCRE2_NEVER_BACKSLASH_C` и назвать
контракт совместимым подмножеством PCRE2 с перечисленными ограничениями.
Отдельно определить политику duplicate names, newline/BSR и версии Unicode.
[PCRE2 pattern syntax](https://pcre.org/current/doc/html/pcre2pattern.html).

### P1. Безопасность интерполяции обещана без определения допустимых позиций

§6, строки 309–335: «вставить `Regexp.escape(value)`» недостаточно как полная
спецификация. Нужно определить, где допустима вставка: обычная последовательность
атомов, character class, quantifier, имя группы, escape, `\Q…\E`.

Например, `r"^[#{value}]+$"` с `value = "a-z"` не должен незаметно превращать
пользовательский текст в диапазон. Текущий `Regexp.escape` не экранирует `-`,
пробелы и `#`; его нельзя без пересмотра переносить в обещанный контракт
с character classes и `(?x)`.

Предлагаемый v1: отверстия разрешены только там, где допустимо целое выражение
regexp; обычная строка вставляется как одна сгруппированная буквальная
последовательность. Вставки внутри классов, escape-последовательностей,
квантификаторов и других незавершённых конструкций диагностируются. Экранирование
обязано сохранять данные при extended mode; до него не должно быть ручного
`Regexp.escape`, иначе получится двойное экранирование.

У `Regexp.fragment` отдельная проблема композиции. Валидный фрагмент `a|b`
в `r"^#{fragment}$"` при простой конкатенации становится `^a|b$` и допускает
`ax` и `xb`. Нужна вставка как `(?:a|b)`. Этого всё ещё недостаточно для
числовых backreferences и конфликтующих имён групп: следует определить их
перенумерацию/область действия либо ограничить такие фрагменты в v1.
Проверка «фрагмент отдельно компилируется» не доказывает корректность композиции.

### P2. Большинство литералов в примерах синтаксически неверны

§1, §2.3, §4–7, §14–16 используют `r"""\d+"""`. Lexer выдаёт
`AMB_TEXTBLOCK_OPENER`. Исправление — `r"\d+"`, а не ослабление правил text blocks.

Настоящий многострочный пример §2.1 имеет другую ловушку: text block сохраняет
последний перевод строки. Воспроизведение с `^[0-9]+$` даёт source длиной 9
и не находит `"123"`. Для форматируемых regexp-блоков показать явный `(?x)`
или предлагаемый суффикс `x`; literal whitespace должен оставаться предсказуемым.
Также §2.3 должен учитывать всю нормализацию text block, включая trailing
whitespace и line joining, а не обещать только dedent.

### P2, исправлено. Компилятор не публиковал результат условия в `$_`

§4, строки 218–226, описывает желаемое поведение. При первоначальной проверке
обнаружена ошибка lowering: условие не обновляло `$_` перед входом в ветку.
Воспроизведение до исправления:

```sputnik
"before"
if "port=8080" =~ r"(\w+)=(\d+)":
  print($_)  # before
```

Исправление публикует итог целого условия до входа в выбранную ветку, сохраняя
прежнюю семантику внутри `and` / `or`: их операнды сами не публикуют
промежуточные результаты. В regexp-условии `$_` теперь содержит Match.
Именованное связывание остаётся отдельной возможностью для локальной переменной:

```sputnik
if m = r"(\w+)=(\d+)".match(input):
  config[m[1]] = Int.parse(m[2])
```

Общий путь source conditions теперь явно понижается с `HLastSet`; исправление
применяется к regexp и другим условиям. Поддержка этого expression добавлена
в bytecode emitter и MIR lowering.

### P2. Пример `case` использует predicate как pattern

§14, строки 561–564: `when pat.full_match?(value)` не является guard.
В текущей сборке, после исправления кавычек, этот пример заканчивается
диагностикой `matcher-expression pattern is missing expr`. По контракту `case`
результат выражения в позиции pattern также не означает «если true».

Рабочая форма:

```sputnik
case value:
  when _ if r"\d+".full_match?(value):
    print("matched")
```

Для одного предиката обычный `if` короче и яснее.

### P2. Правило zero-width пропускает непустое совпадение на той же позиции

§10, строки 458–461, требует сразу перейти на следующий codepoint.
Для `(?:|a)` на `"a"` это выдаст два пустых совпадения и потеряет `"a"`.
PCRE2 global matching выдаёт `""`, `"a"`, `""`: после пустого результата
сначала допускается непустой матч на той же позиции.

Нужно зафиксировать один алгоритм для `scan`, `each_match`, `replace` и `split`,
включая конец строки и CRLF. Если намеренно выбирается более простое поведение,
его нельзя называть стандартным без примера отличий.
[PCRE2 iteration API](https://pcre.org/current/doc/html/pcre2api.html).

### P2. `^…$` не гарантирует full match

§4, строки 235–240, подсказывает anchors как альтернативу `.full_match`.
В PCRE2 `^\d+$` успешно ищет `123` в `"123\n"`; с `m` границы становятся
границами строк. Использовать `.full_match` либо `\A…\z` и не представлять
`^…$` как эквивалент проверки всей строки.
[PCRE2 anchors](https://pcre.org/current/doc/html/pcre2pattern.html).

### P2. Match limit не является общим бюджетом операции

§8, строки 382–390: полезная защита, но обещание пригодности для сервисов
слишком широкое. В PCRE2 при unanchored search счётчик может начинаться заново
на каждой стартовой позиции; JIT учитывает лимит иначе. Это не deadline и не
общий бюджет `scan`/`replace`. Память, размер результата и стоимость компиляции
тоже требуют отдельного решения.

Задать единицы/границы match limit, политику depth/heap/JIT limits, отображение
ошибок и ограничение суммарной работы. Не обещать идентичное срабатывание
лимитов между версиями движка и JIT/интерпретатором. Зафиксировать версию
PCRE2/Unicode для воспроизводимых frozen images.
[PCRE2 resource limits](https://pcre.org/current/doc/html/pcre2api.html).

### P2. Обычный string tag и специальный `r` пока имеют разные правила

§1–2 и DoD обещают импортируемый/переименуемый макрос. Lexer разрешает raw
escapes по проверке имени `r`, а expander обрабатывает его раньше обычных tags.
`from Regexp import r as rx; rx"\d+"` (на отдельных строках) воспроизводимо
падает на `AMB_STRING_BAD_ESCAPE`.

Это следует отметить как незавершённую интеграцию, не как новую норму языка.
Исходные escape parts уже существуют (`AstStringEscape.source`/`value`);
§2.3 нужно описать их действительную форму или явно предложить новый API,
а не повторно планировать наличие двух представлений вообще.

### P2. Не хватает решений для граничных случаев API

Перед реализацией зафиксировать:

- `from:` — codepoint offset, допустимые границы, отрицательные значения,
  поиск от конца строки; поиск должен сохранять исходный subject для anchors
  и lookbehind, а не работать на отрезанном суффиксе.
- `split` — внутренние пустые поля, пустой subject, zero-width separators,
  `limit: 0/1/negative`, остаток после достижения limit. Считаются ли captures
  частью limit; как представлены unmatched captures. Последнее влияет на
  обещанный тип `List[Str]`.
- Replacement — неизвестная и unmatched группа, `$100`, `${1}`, проверка
  ошибочной replacement при отсутствии совпадений, `count: 0/negative`.
  Для буквальной пользовательской replacement нужна отдельная понятная форма:
  например, уже предусмотренный block, возвращающий строку без `$`-разбора.
- Ошибки — §3/5/8/9 ссылаются на `Regexp.CompileError`, `Regexp.GroupError` и т. д.,
  §11 объявляет `RegexpCompileError`, `RegexpGroupError`. Выбрать канонические
  имена либо явно объявить aliases.
- `Pattern.flags` — внешние флаги или эффективные настройки? Scoped inline
  flags нельзя полноценно представить одним плоским списком.
- `literal: true` — точная буквальная семантика при `extended: true`; текущий
  `escape` удаление значимых пробелов движком не предотвращает.
- Compile-time diagnostics — карта смещений после dedent/line joining и
  политика для динамической интерполяции. Нужен доступный компилятору тот же
  синтаксис движка, что и runtime.
- Статические литералы — переиспользование compiled program; для динамических
  шаблонов, если вводится cache, он должен иметь определённую границу размера.

## 3. Операторы

| Вариант | Результат | Отрицание | Оценка |
| --- | --- | --- | --- |
| `text ~= pat`, `pat ~= text` | `Bool` | `not (text ~= pat)` | Рекомендую, если важна дальнейшая общая семантика |
| `text ~= pat`, `pat ~= text` | `Match?` | `not (text ~= pat)` | Минимальная замена `=~`, сохраняет извлечение захватов оператором |
| `text matches pat`, `pat matches text` | `Bool` | `not (text matches pat)` | Явное сопоставление; `~=` можно оставить числовой близости |

Первый вариант читался бы как «соответствует». Для regexp предлагаю сохранить
search semantics, чтобы смена символов не скрывала ещё и смену поведения.
Но «примерно равно» не должно обещать целостное совпадение: `"abc123" ~= r"\d+"`
при этом истинно. Если именно это кажется неправильным, лучше явно выбрать
full-match семантику до внедрения или использовать третий вариант.

Предлагаемый синтаксис:

```sputnik
if text ~= r"\d+":
  print("contains digits")

if r"\d+" ~= text:
  print("same predicate")

if not (text ~= r"\d+"):
  print("no digits")

if m = r"(\w+)=(\d+)".match(text):
  print(m[1], m[2])
```

`not` уже имеет приоритет ниже comparisons, выше `and/or`
(`frontend/parser/parser.cpp:4021`), поэтому при сохранении precedence 4 будет
работать и `not text ~= pat`. В учебных примерах скобки делают границу очевидной.
Нового отрицательного оператора `!~`, `!~=` или `~!=` не требуется.

Контракт симметрии должен определять dispatch, а не только две перегрузки:

1. Оба операнда вычисляются ровно один раз слева направо.
2. По паре типов определяется одна операция; положение Pattern неважно.
3. В v1 разрешены только `(Str, Pattern)` / `(Pattern, Str)`. Две строки,
   два Pattern и неподдерживаемые пары дают `TypeError`.
4. Ошибки движка/лимитов не превращаются в `false` и не запускают попытку
   «поменять стороны и повторить».
5. Для пользовательских расширений нужна одна регистрация неупорядоченной
   пары типов/однозначная роль matcher. Два независимых произвольных метода
   `lhs.~=(rhs)` не гарантируют симметрию.
6. `~=` не заменяет `==` и не участвует в equality/hash коллекций.

Расширять удобно через явные matcher values: glob, сравнение текста по заданным
правилам, числовая окрестность с заданными absolute/relative tolerances.
Например, будущая форма `value ~= Approx(10, abs: 0.01)` и переставленные
операнды могут иметь одинаковую предикатную семантику. Имена здесь иллюстративны.
Не вводить сразу неявную fuzzy-семантику `Str ~= Str` или универсальный epsilon
для любых чисел. Для чисел отдельно определить NaN, infinities и scale.
Симметричность не обещает транзитивности приблизительного сравнения.

Если принципиальна форма `if m = text ~= pat`, второй вариант тоже последователен,
но будущий результат оператора станет зависеть от типов: Match? для regexp,
Bool для чисел. Тогда общим контрактом будет только truthiness; это менее
удачное основание для универсального оператора сравнения.

Поскольку `=~`/`!~` уже существуют, нужна явная миграция. При Bool-варианте нельзя
механически менять `=~` на `~=` в коде, который использует Match: такие места
переходят на `.match`. Возможен ограниченный период устаревающих aliases, но
сохранение их навсегда оставит сразу несколько конкурирующих способов записи.

## 4. Модификаторы

Ответ на пример `/[a-z]/mi`:

- По проекту §7: `r"(?mi)[a-z]"`. Суффикс там явно исключён.
- В текущем runtime: этот inline-синтаксис падает с `RegexpCompileError`;
  `Regexp.compile("[a-z]", flags: "i")` работает, `flags: "mi"` отвергается.
- Предлагаемый канонический литерал: `r"[a-z]"mi` или `r'[a-z]'mi`.

Для динамического pattern сохранить читаемые keywords из документа:

```sputnik
# Предлагаемый API после перехода на PCRE2:
pat = Regexp.compile(source, multiline: true, ignore_case: true)
```

Inline `(?mi)` оставить, особенно для scoped flags вроде `(?i:part)`.
Суффикс задаёт начальные опции компиляции, inline flags уточняют их по правилам
PCRE2. `mi` и `im` равнозначны. Неизвестный флаг — диагностическая ошибка;
для повторных букв выбрать и описать одну политику, например ошибку-подсказку.

`m` меняет `^`/`$`, `s` — точку, `x` — whitespace/comments, `i` — регистр.
В `[a-z]` без anchors флаг `m` ничего не добавляет. `u` не нужен при всегда
включённых UTF/UCP; `g` не нужен, потому что число совпадений задаёт операция
`match`/`scan`/`replace`.

Архитектурно суффикс стоит передавать в общий `Ast.StringTemplate` как данные
вместе со span. Parser распознаёт соседство `tag + literal + suffix`, provider
проверяет смысл букв. Опции должны попасть в компиляцию до валидации pattern.
Это позволяет алиасам тега работать одинаково и не добавляет ещё одно особое
правило для имени `r`.

Варианты `ri"…"`/`rim"…"` засоряют namespace комбинациями провайдеров.
Вариант `r"…".with_flags(...)` хуже для `x`: исходный pattern может не
компилироваться до применения extended mode. Текущий отказ от suffix как
«parser churn with little payoff» стоит заменить реальным решением с учётом
коротких string tags и обнаруживаемости модификаторов.

Отдельными программами проверены короткие теги, оба порядка `=~`, импорт/alias,
triple quotes, завершающий newline блока, `$_`, binding Match, `case`/guard,
интерполяция, недостижимый ошибочный литерал, UTF-8 capture и флаги.
Через установленный PCRE2 10.47 проверены empty global matches, `^…$`, `\C`,
inline-флаги и precedence вставленной альтернативы. Эти пробы не являются
заявлением о поддержке PCRE2 в Sputnik.

Первоначальное ревью не меняло дизайн и реализацию. Последующее исправление
публикации условия в `$_` отмечено выше; остальные предложения остаются ревью.
